# goit-cs-hw-04

Паралельний пошук ключових слів у текстових файлах. Дві реалізації: на `threading` і на `multiprocessing`.

## Структура

- `common.py` - спільний код: збір файлів, розбиття списку між воркерами, пошук у файлі, злиття результатів
- `threading_search.py` - версія на потоках, результати збираються у спільний словник під `Lock`
- `multiprocessing_search.py` - версія на процесах, кожен процес кладе свій словник у `Queue`
- `main.py` - запускає обидві версії, порівнює час і перевіряє, що результати збігаються
- `texts/` - тестові файли

## Запуск

```bash
python main.py thread process gil
python main.py -d texts -w 4 thread process gil

python threading_search.py thread gil
python multiprocessing_search.py thread gil
```

Аргументи: список слів (обов'язково), `-d` каталог з `.txt` файлами (за замовчуванням `texts`), `-w` кількість потоків або процесів (за замовчуванням 4).

## Як працює

Файли з каталогу збираються рекурсивно, список ділиться на `workers` частин через зріз `files[i::parts]`. Кожен воркер читає свої файли і шукає всі ключові слова без урахування регістру.

Результат обох версій: словник, ключ - слово, значення - список шляхів до файлів, де воно знайдене.

У версії на процесах чергу треба вичитати до `join()`. Дочірній процес з великим результатом блокується на записі в pipe, і `join()` без цього не завершиться.

Помилки читання файлу (немає доступу, файл зник, бінарний вміст) логуються, файл пропускається, решта обробляється далі. Відсутній каталог завершує програму з повідомленням.

```

    texts/async.txt
    ...
'process': 5 file(s)
    ...
'gil': 3 file(s)
    ...

threading:       0.0005 s
multiprocessing: 0.1500 s

```

На малих файлах потоки швидші: старт процесу коштує більше, ніж читання файлу. Перевага процесів з'являється на великих обсягах тексту, коли пошук стає CPU-навантаженим і впирається в GIL.
